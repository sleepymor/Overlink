## 1. What "30%" means

The GDD defines no weighted completion metric. This plan is a **100-point implementation budget**;
the items marked **NOW** total exactly **30 points** and aim at one outcome:

> A locally playable match, driven by real authored card data, that a person can start and finish.

It is a planning estimate, not a measurement of the game's completeness.

**Total: 30 points.**

### Trade made to fit the tooling

Combat/effects 4→3, pilot set 4→2, opponent 4→2. The cost is a smaller initial effect set.
The reason is that the pilot set is a *deliverable* while Card Manager is *infrastructure*: every
later card depends on it, and retrofitting tooling against already-authored data repeats the
`CardData.cs` placeholder mistake one layer up. At 60 cards (three factions) it stops being
merely inefficient.

### Guardrail for automated edits

OpenCode has no built-in protection for the working tree. Every run uses an explicit file
allowlist plus `git diff --name-only` before and after, refusing any run that touches the
protected set. A `git worktree` would be stronger but mutates git metadata and needs approval.

### Protected paths

```
Assets/Scripts/Net/**          (existing uncommitted work)
Assets/Resources/**            (Google auth settings)
ProjectSettings/**             (except an approved build-settings change)
GDD/**
Assets/Scenes/NetPresenceDemo.unity
Assets/Scenes/SampleScene.unity
```

## 7. Scene strategy

`.unity` files are YAML, so they can be edited without the Editor — but the risk order matters:

1. **Runtime construction** — lowest risk, and already this project's pattern (`CardView.Create` builds cards procedurally; there are no card prefabs).
2. **Editor script** — low risk. Unity resolves every reference, so the result is correct by construction. This is the standard for all scene work.
3. **Direct YAML edit** — highest risk. Hand-managed `fileID`s and GUIDs produce silent null references no compiler catches. Only when nothing else is possible, with a backup and a diff review.

**`Gameplay.unity` is generated by `Assets/Editor/BuildGameplayScene.cs`**, not hand-written.
Menu: `Overlink > Scenes > Build Gameplay Scene`.
Batchmode: `Unity.exe -batchmode -quit -projectPath <project> -executeMethod Overlink.EditorTools.BuildGameplayScene.BatchBuild`

| Tag | Meaning |
|---|---|
| `v0.17.0` | Plan baseline, current `master` |
| `v0.17.1` | M1 Core schema complete |
| `v0.17.2` | M2 Card Manager usable |
| `v0.17.3` | M3 Match loop resolves |
| `v0.17.4` | M4 Playable slice |

Annotated tags only: `git tag -a v0.17.1 -m "M1: Core schema and validator"`.

### Commit messages

```
<area>: <imperative summary>

<why, not what — the diff shows what>
```

Areas: `core`, `cards`, `match`, `ui`, `net`, `editor`, `docs`, `chore`.

### Rules

- Never commit `Library/`, `Temp/`, `Logs/`, `Build/`, `UserSettings/` (already ignored).
- Never force-push `master`.
- Tag only from a green build.
- One milestone per tag; no tag on a dirty tree.

### Repository hygiene already in place

`.gitignore` covers Unity generated folders, IDE files, test-runner bootstrap scenes, and OS noise.
