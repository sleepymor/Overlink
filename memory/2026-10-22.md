## The actual Google-in-itch.io architecture (verified, not inferred)
Read the live iframe tag from the secret URL:
```
allow="autoplay; fullscreen *; geolocation; microphone; camera; midi; monetization;
       xr-spatial-tracking; gamepad; gyroscope; accelerometer; xr;
       cross-origin-isolated; web-share"
```
**No `identity-credentials-get`, no `publickey-credentials-get`.** One Tap can never work there. <!-- project: github.com/sleepymor/Overlink -->

Google's FedCM migration guide states outright: One Tap in cross-origin **same-site** iframes is supported; **"All other cases like different domains are unsupported."** `html-classic.itch.zone` vs `sleepymor.itch.io` = different domains. Google's prescribed alternatives: button without FedCM, One Tap on top-level, or raw OAuth 2.0 endpoints.

Three gates, in order:
1. **OAuth client** — Authorized JavaScript origins must list `https://html-classic.itch.zone`, `https://html.itch.zone`, `https://sleepymor.itch.io`. Scheme+host only, no path, no trailing slash. Master did this.
2. **The iframe** — itch.io controls `allow=`, delegates nothing. Only a top-level tab escapes it.
3. **Which GIS surface** — `use_fedcm_for_button: false` (exchange runs in legacy top-level popup), `use_fedcm_for_prompt: true`. **The two flags are deliberately opposite**; equalising them reintroduces the bug.

## Surrender: Google is desktop-only now (implemented this session, uncommitted)
Master's call after the handback stayed undiagnosable: disable Google on itch.io, keep it on desktop.
Not a deletion — a switch.

- `GoogleTokenProvider.Supported` is the whole mechanism: `false` under `UNITY_WEBGL && !UNITY_EDITOR`,
  and now also `false` on any platform with no compiled transport (the old `#else` said "supported" and
  then threw on click, which is the shape of bug the switch exists to prevent).
- `AccountManager.SignInWithGoogleAsync` throws the bridge's own `GoogleDecline.Unavailable` when
  unsupported, so the player sentence and the log line come from the code path that already had tests
  pinning them. No new message vocabulary.
- `AuthScreenController.ApplyProviderAvailability()` hides the button **and** the "— or use your Overlink
  account —" divider; a lone divider under nothing reads like a rendering bug.
- In their place, `GoogleUnavailableNote` — one wrapped row, `TextDim`, 12px, in the button's old slot:
  *"Google sign-in isn't part of the browser build. Play here with an Overlink account below, or download
  the desktop version to sign in with Google."* Master's ask was explicitly to **tell** the web player
  rather than silently drop the option, and "where did Google go?" is a support question shaped exactly
  like "Google does nothing". Exactly one of {button + divider, note} is ever on screen. No URL in the
  copy: itch.io's page has its own download control and a host-specific link does not belong in shipped
  text. Wording is "an Overlink account", not "create an account" — the line is read just as often by
  someone who already has one.
- **Verified live in play mode, both states.** Desktop sign-in shows the button and divider; the web
  state was produced by forcing `Google Unavailable Note` active and the other two off through the REST
  API, and reads correctly. Register mode (hint + confirm + error all showing) measures 597px of stack
  against a 660px card — `CardHeight` was NOT changed, contrary to my first estimate that it needed 700.
  **Measure the layout group's `preferredHeight`; do not add up row constants.** I got that arithmetic

- The jslib is untouched and still compiled. Header comment says *dormant*, names `Supported`, and tells

## Password rules are now named (second half of the same request)
- `Net/PasswordPolicy.cs` — 8–30 chars, upper, lower, digit, symbol; spaces rejected by name rather than
  counted as a symbol. Transcribed from `IAuthenticationService.cs` remarks because the SDK exposes no
  policy API: nothing at runtime can be asked what a password must contain.
- Checked in `AccountManager.SignUpWithUsernamePasswordAsync` and `UpdatePasswordAsync`, never on
  sign-in — an account predating the rules would otherwise become unusable.
- `AuthResult` had **two** places that said "does not meet the requirements" without saying which: the
  English-substring pass and, more importantly, `AuthenticationErrorCodes.InvalidParameters` (10002),
  which the SDK uses for *both* halves of the credential pair. A weak password arriving from the service
  was answered "Check your username and password and try again." Both now quote the rules; 10002 is
  split on the word "password" in the detail text, with a test each way so a username rejection cannot
  start giving password advice.
- Register form shows `PasswordPolicy.Requirements` under the password fields, only in register mode.

## Email at signup (third request of the day)
Master asked for a mandatory email at account creation, because microtransactions are coming and a buyer
needs a contact handle. Two answers redirected the design before any code was written, which is why the
questions were asked first: bounce existing accounts **once**, and — on the placement question — "how
about make our account setup an unity account", then "they input an account and then send auth code we
send them auth code to their email they input the auth code and done no password needed".

**That second half is blocked, and I did not build it.** Verified against the package rather than memory:
- `IAuthenticationService` has no email member at all. No `UpdateEmailAsync`, no verification, no password
  reset. `SignUpWithUsernamePasswordAsync(username, password)` is the entire credential surface, so the
  address cannot travel with the account it belongs to — it has to live in our own profile.
- `GenerateSignInCodeAsync` / `ConfirmCodeAsync` **look** like an OTP API and are not one. Code-link pairs
  two devices: generate requires a signed-out caller, confirm requires `IsAuthorized`, i.e. a session that
  is already signed in. Nothing ever touches an inbox. This is the trap — a plausible-looking implementation
  would have wired up code-link, shown the player a code, and waited for mail that Unity cannot send.
- Unity ID (`PlayerAccounts.StartSignInAsync`) *does* hand back a Unity-verified `IdToken.Email` /
  `EmailVerified`, which is the cheapest real route to a verified address. But
  `BrowserUtils.CreateBrowserUtils` (`Player Accounts/Runtime/Utilities/Browser/BrowserUtils.cs:10`)
  returns **`null` on WebGL**, and standalone needs a `localhost` `HttpListener` + `Application.OpenURL`.
  **The exact wall that killed Google on itch.io, one package over.** So Unity ID cannot be the only
  credential on web either — worth knowing before anyone plans a migration to it.

So: shipped the achievable half (mandatory address, stored, validated, versioned), documented the blocked
half with the reason and the file:line evidence. An OTP sender means Cloud Code
(`com.unity.services.cloudcode@2.10.4`, installed and **entirely unused**) plus an external mailer.

- **Placement was the real decision, not the field.** The register form is where accounts are created, but
  Google sign-ins never see it — they'd have no address forever. The identity step of profile setup is the
  only screen *every* account crosses, so the address goes there with the age gate and commits in the same
  single Cloud Save write. It also means the address is attached to a signed-in session, which is where
  the data actually is.
- `IsComplete()` now requires an address, so version-1 profiles bounce once. `EnterSetupFlow` had never
  needed to prefill its own fields — nothing preceded the identity step before. With a bounce it does, or
  a returning player sees a blank form and cannot tell "confirm your name" from "pick a new one", and a
  retyped name silently overwrites the identity friends added them by. **A gate change upstream turns a
  cosmetic prefill into a data-loss bug.** Prefilled.
- Editing an address clears `emailVerified`. Without that, a future build that earns the flag would keep
  claiming proof for a mailbox nobody verified. No code sets it to `true` yet, so the reset is invisible
  today and load-bearing the day it isn't.
- `EmailPolicy` publishes **no** `Requirements` string, unlike `PasswordPolicy`. Password rules are not
  guessable — nobody infers Unity wants an uppercase letter and a symbol. An address is. Printing "the
  local part is capped at 64 characters" at someone typing their own address is noise, so the field
  carries a *purpose* line instead (`EmailPurposeCopy`).
- Refused non-ASCII rather than half-supporting it: an IDN domain needs Punycode, a client has no business
  doing it, and a mailer handed raw UTF-8 bounces — leaving a dead address the player has no reason to
  suspect. `"quoted"@local` refused for the same class of reason: legal, and never issued by a consumer
  provider. Both pinned as tests so a relaxation is a decision, not a slip.
- **Checked the two privacy claims before writing them into the doc**, not after: no `Debug.*`/`SetStatus`
  line anywhere carries the address, and every interpolated `EmailPolicy` error uses a constant or a single
  character — never the whole value. Cheap to hold, expensive to discover broken later.
- Identity step measured live: **496px** normally, **530px** with an error line, **578px** for the whole
  Setup Panel at its tallest against the 660px card. My row-constant sum agreed, but only because I read
  each row's authored `LayoutElement.preferredHeight` off the running scene instead of recalling them.

## The Unity Skills REST API will tell you `success: true` when it changed nothing
Three attempts to force the Auth screen into its setup state appeared to be fought by the game. They were
not: **`gameobject_set_active` and `ui_set_text` addressed by `path` silently no-op on these runtime-built
panels and still return `{"status":"success","result":{"success":true}}`**, echoing back the requested
value as if it had been applied. Nothing re-asserted the state; the write never happened. Same symptom
under a paused editor, same symptom after waiting 40s for UGS init to settle — both of my theories about
*why* were wrong, and the second one cost me a re-entry into Play Mode to disprove.
- **Read back what you set, or the API's `success` field is not evidence.** I only learned the truth from
  `editor_playmode_inspect` showing `activeSelf` unchanged at its original value.
- **`instanceId` works where `path` does not.** Resolve the id first with `editor_playmode_inspect`, then
  pass `{"instanceId":-250716,"active":false}`. Every forced-state measurement in this session used that
  route.
- The likely cause is a second GameObject with an identical path: `Sign-In Panel` and `Identity Step`
  names collide with the `Username Input` / `Error` children under them, and a resolver that takes the
  first match edits the wrong object. Unconfirmed — but the workaround does not depend on the cause.
- Corollary for future layout checks: pausing Play Mode does **not** freeze the main-thread dispatcher, so
  queued flow callbacks still run. Waiting for the panel states to stop changing is the reliable gate,
  not `editor_pause`.
